# DecentPilgrimageBaseV1

## Reuse and version decision

The receiving worktree contains `public/contracts/DecentPilgrimage.sol` and
`public/contracts/DecentPilgrimage_v0.2.sol`; they are byte-identical legacy
sources and both existing ABIs remain unchanged under `public/abis/`. Their
location-level token amounts are claimed by the first eligible caller and the
legacy claim pays every token in a loop. The v1 work therefore builds a
separate, versioned contract rather than copying or replacing either deployed
source/ABI. It adapts the existing location fields (coordinates in
microdegrees, radius in meters, mission text) while changing reward
authorization to organizer-approved, per-participant claims.

The work was intentionally bounded to this receiving worktree; no sibling
repository or external donor source was searched. No payroll or real-world
transfer feature is included.

## Legacy migration status

The three legacy addresses are now confirmed deployed on **Polygon mainnet
(137)**, with existing token custody in the current frontend journey.
Earlier Optimism-only probes checked the wrong network. See the dated
[Polygon findings](#legacy-polygon-findings-read-only-2026-11-02) below for
addresses, pinned blocks, actual journey names and decoded funding/stop data.
Contract source matching, a complete token inventory and organizer obligations
remain unresolved. Do not treat v1 as a migration of state or a fulfillment
of legacy promises. Any migration/reversion requires an independent,
steward-approved review of historical deployment and event records before
deployment or funding. The old source and ABI files remain unchanged.

## Roles and payout model

- The owner is the organizer/steward. Use a well-governed multisig or equivalent
  for production ownership. The owner approves sponsors, creates/activates
  locations, reserves funded token budgets, approves/cancels participant
  claims, releases unused budget, and recovers unallocated funds.
- An approved sponsor can fund native Base ETH with `fundNative()` and
  `msg.value`, or supported ERC-20s with `fundToken(token, amount)`. Sponsors
  cannot allocate rewards, approve claims, or recover funds.
- A participant can call `claim(locationId, token)` only for an active location
  and only after the owner has approved that exact participant/token/amount.
  Each participant can receive at most one payment per location and token.
- `locationCount()` and `getLocation(locationId)` provide location data.
  Latitude is bounded to [-90,000,000, 90,000,000] microdegrees and longitude
  to [-180,000,000, 180,000,000] microdegrees at creation; these are coordinate
  validity checks, not proof of presence or geofencing.
  `getLocationTokens(locationId)` explicitly returns dynamic token addresses;
  the private location record is not relied on to expose dynamic arrays through
  an autogenerated mapping getter.
- `allocationRemaining(locationId, token)`, `pendingApprovedAmount(...)`,
  `approvedClaimAmount(...)`, and `hasClaimed(...)` support organizer and
  participant state displays. Contract events are the indexable history.
- Browser/device location is advisory only. It never authorizes or triggers a
  payout; organizer approval is the authorization.
- This contract is not payroll, does not schedule/activate payroll, and does
  not make arbitrary automatic payments. A transaction is paid only when a
  participant submits an approved claim.

## Token accounting and limits

`accountedBalance[token]` tracks funding minus claims and owner recovery.
`totalAllocated[token]` reserves the remaining location budgets. The invariant
is `totalAllocated <= accountedBalance`; recovery can use only their
difference. For native Base ETH, use `address(0)` as the token key everywhere:
`fundNative()` records `msg.value` in wei under `accountedBalance(address(0))`,
and `addAllocation`, `approveClaim`, `claim`, `releaseAllocation`,
`recoverToken`, and `getLocationTokens` use that same zero-address sentinel.
ETH amounts are in wei (18 decimals). ERC-20 amounts remain in that token's smallest unit; integrations should read
each ERC-20's decimals rather than assuming USDC or any other token has 18
decimals. The initial intended Base assets are native ETH and USDC; USDC and
other exact-transfer ERC-20s use the same generic interface. No token address
is configured by this contract release. An approval reserves against its
location/token allocation in aggregate, preventing approvals from exceeding
the budget. The owner must cancel all pending approvals before releasing any
remaining allocation.

Native ETH is accepted only through `fundNative`; bare transfers are not the
funding interface. ETH payouts use checks-effects-interactions and a
reentrancy guard. Only standard, non-rebasing ERC-20s with exact transfer
amounts are supported. ERC-20 funding is checked against the contract's
balance delta; claims and recovery check both the contract's debit and the
recipient's credit. Fee-on-transfer tokens are rejected on either path.
ERC-20 amounts are raw token units. Tokens sent directly without `fundToken`
and ETH forcibly sent without `fundNative` are unaccounted surplus and are not
included in the normal recovery ledger.

## Stable frontend interface

Artifact ABI: `contracts/abi/DecentPilgrimageBaseV1.json` (regenerate with
`npm run abi:export`). Stable write calls:

```text
fundToken(address token, uint256 amount)                    // approved sponsor
fundNative() payable                                         // approved sponsor; msg.value in wei
createLocation(string name, int256 latMicrodegrees,
                int256 lngMicrodegrees, uint256 radiusMeters,
                string mission)                             // owner
addAllocation(uint256 locationId, address token, uint256 amount) // owner; address(0) = ETH
approveClaim(uint256 locationId, address token,
             address participant, uint256 amount)            // owner; address(0) = ETH
cancelClaimApproval(uint256 locationId, address token,
                    address participant)                     // owner
claim(uint256 locationId, address token)                     // approved participant; address(0) = ETH
```

The current ABI also exposes `setSponsor`, `setLocationActive`,
`releaseAllocation`, and `recoverToken` for owner controls; pass
`address(0)` to release/recover ETH. Stable read calls include
`pilgrimageName`, `owner`, `locationCount`, `getLocation`,
`getLocationTokens` (address zero entries mean ETH), `approvedSponsors`,
`accountedBalance`, `totalAllocated`, `allocationRemaining`,
`pendingApprovalCount`, `pendingApprovedAmount`, `approvedClaimAmount`, and
`hasClaimed`. Use `contracts/config/networks.json` for chain IDs and explorer
URLs. It intentionally contains no contract addresses; add an address only
after a real deployment has been independently confirmed and source-verified.

The existing public UI uses the legacy ABI. A v1 UI must explicitly select v1
by chain and configured deployed address, use the v1 ABI, request ERC-20
allowance before `fundToken`, send native ETH as `fundNative({ value })`
without token approval, and show inactive, unapproved, or unavailable states
without implying a payout.

## Deployment and source verification

No deployment has been performed. Before any future deployment, review the
contract and tests, use a dedicated deployer with a limited balance, confirm
the network and constructor values, and obtain the required steward approval.
Do not paste keys into source control or shell history; supply
`DEPLOYER_PRIVATE_KEY`, the chosen RPC variable, `PILGRIMAGE_NAME`, and
optionally `INITIAL_OWNER` through an approved secret manager or protected
environment. `INITIAL_OWNER` defaults to the deployer if omitted; prefer the
steward multisig for production.

Example commands for an explicitly authorized deployment:

```sh
npm ci
npm run compile
BASE_SEPOLIA_RPC_URL="$BASE_SEPOLIA_RPC_URL" \
DEPLOYER_PRIVATE_KEY="$DEPLOYER_PRIVATE_KEY" \
PILGRIMAGE_NAME="..." INITIAL_OWNER="0x..." \
npx hardhat run scripts/deploy.js --network baseSepolia
```

Record the confirmed deployment address, transaction, constructor arguments,
and chain ID outside this repository until reviewed. Verify against the actual
compiled Hardhat artifact with the same source revision, compiler settings,
and constructor arguments:

```sh
ETHERSCAN_API_KEY="$ETHERSCAN_API_KEY" \
BASE_SEPOLIA_RPC_URL="$BASE_SEPOLIA_RPC_URL" \
CONTRACT_ADDRESS="0x..." PILGRIMAGE_NAME="..." INITIAL_OWNER="0x..." \
npx hardhat run scripts/verify.js --network baseSepolia
```

For Base mainnet, use `BASE_RPC_URL` and `--network base` instead.
`ETHERSCAN_API_KEY` must be a unified Etherscan.io V2 key, not a legacy
Basescan-specific key. Both chains use `https://api.etherscan.io/v2/api`;
the installed `@nomicfoundation/hardhat-verify` 2.1.3 selects V2 from the
single string `etherscan.apiKey` and supplies the chain ID (8453 or 84532).
The explorer browser URLs remain Basescan and Sepolia Basescan. Do not use
network-specific API-key maps or deprecated V1 API endpoints. Verification
requires an Etherscan API plan supporting the intended chain; this release
does not test key validity, plan availability, or explorer acceptance.

The helper rejects missing key/constructor inputs, invalid/zero addresses,
unsupported V2 configuration, and an RPC chain-ID mismatch before source
submission. It passes the exact fully qualified compiled artifact name and
constructor arguments to Hardhat's verification plugin, which uses the
corresponding compiler/build artifact. `npx hardhat test test/Verification.js`
validates both chains and failure gates offline using a synthetic key, mocked
RPC chain response, and mocked verification task. It makes no explorer
request and does not submit private source or credentials.
Verification is useful source transparency; it does not guarantee removal of
wallet warnings. MetaMask simulation results, phishing reports, and
reputation/risk signals are independent of source verification.

Never report deployment or verification success unless the corresponding
transaction/explorer state has been checked on the intended chain.
# Legacy Polygon findings (read-only, 2026-11-02)

The earlier Optimism probes were the wrong network for these deployments.
Polygon mainnet (137) returns deployed bytecode at all three legacy addresses:

- [Registry](https://polygonscan.com/address/0x4a50bbf238279E7F816Ef0Eaf523ae27962EC5E2):
  3,274 runtime bytes. `getPilgrimages()` at block 96638974 lists the older
  journey below, not the current frontend journey.
- [Current frontend journey](https://polygonscan.com/address/0x8FD1A345F65D27a3c360933e38CC653E0dE37CC1):
  14,701 runtime bytes; `pilgrimageName()` is **Zerb's Cool Cat Summer**.
  At block 96638944 it has two active test stops and one approved sponsor.
- [Older journey](https://polygonscan.com/address/0x396e0e11E26A3aCfF7BAcBe9d5943b6b4fdD181d):
  11,761 runtime bytes; **DooBetter Blazes the East Coast (2025)**, zero locations
  at block 96638944. The current ABI's `getWhitelistedSponsors()` reverts here:
  historical versions are not interchangeable.

Read-only RPC used PublicNode for current state. Historical transaction access
there required an archive token; dRPC's public Polygon endpoint supplied the
three historical transactions instead. Decoding the successful
`addSponsorTokens` transaction
[`0x758906…f9e29cb`](https://polygonscan.com/tx/0x758906e162dd2657a15d109f3604e9c43bee4e78382e13c1d5650e574f9e29cb)
with the local ABI shows 10e18 raw units of
[`0x81cCeF…00cd78`](https://polygonscan.com/address/0x81cCeF6414D4CDbed9FD6Ea98c2D00105800cd78).
The token reports `SHT`, 18 decimals. At block 96638982, current journey custody
is 10e18 raw units, with 10e18 minus 3 raw units in `sponsorBalances`.
The two successful location transactions assign 1 and 2 **raw units**, not
1 and 2 whole tokens. Their coordinates also contain small raw integers despite
the local source's microdegree convention. Preserve these values; do not silently
reinterpret or migrate them.

Intent in local `public/contracts/DecentPilgrimage.sol` and the ABI:
owner/approved sponsors fund ERC20s and create named geographic stops with token
baskets; owner-approved participants collect a stop's entire remaining basket.
The local source deactivates the stop after collection, tracks collected tokens,
and does not prove physical arrival. It does **not** require the new Base
version's separate approval for every wallet/location/asset/amount. Sponsor
creation of stops and basket-level collection are also different from the new
owner-only location creation and per-asset claims. Those are product differences
to reconcile before treating Base V1 as a faithful replacement.

PolygonScan's current-journey page offered **Verify and Publish**, not verified
source, during inspection. ABI-compatible reads and transaction decoding do not
prove full deployed-source equivalence. This was not a security audit, exhaustive
transfer-history inventory or migration; other token balances and older-journey
obligations remain unestablished. No wallet, write, transfer or source submission
was used. Existing funds must not be treated as abandoned.
